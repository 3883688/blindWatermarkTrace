# Image Ownership and Management Visibility Design

## Goal

Associate every image record with the numeric `users.id` of the account that
uploaded it. Administrators can see and delete every image, while all other
roles can see and delete only images owned by their current authenticated
account.

The deployed database already contains `users.id` and
`image_records.user_id`. The application model does not yet map those columns,
and all six existing image records currently have a null owner.

## Scope

This change covers:

- Mapping the existing numeric user and image-owner columns.
- Backfilling unowned historical images to the configured administrator.
- Associating a validated login token with a database user identity.
- Assigning new image records to the authenticated user in the backend.
- Filtering the image-management list and its statistics by ownership.
- Applying the same ownership rule to image deletion.
- Sending the login token from the Vue frontend and handling expired sessions.

The serialized image document already has a `user_id` field used by watermark
payloads and trace results. That field remains unchanged. In this design,
`image_records.user_id` is a relational owner ID and is not merged into or
substituted for `data.user_id`.

Direct `/uploads` URLs, trace-result visibility, dashboard-wide statistics,
and administrator-only protection for the user and role APIs are outside this
change.

## Storage Design

Update the SQLAlchemy table metadata to match the deployed schema:

- `users.id` is the integer primary key and is generated by the database.
- `users.username` remains the unique login and display identifier. The
  deployed data currently has no duplicate usernames even though its table
  does not declare a unique constraint.
- `image_records.user_id` stores the numeric `users.id` of the uploader. Fresh
  schemas declare this relationship as a foreign key; startup validation
  enforces the same relationship for the deployed table, which currently has
  no foreign-key constraint.

Fresh databases create the same shape. Existing databases keep their current
columns. Startup performs an idempotent data migration after the configured
administrator has been seeded:

1. Resolve `ADMIN_USER` to exactly one `users.id`.
2. Set `image_records.user_id` to that ID only where the current value is null.
3. Leave every non-null owner untouched.
4. Verify that usernames are unique and every non-null image owner resolves to
   a user.
5. Fail startup with a non-secret error if the administrator cannot be
   resolved or either integrity check fails.

The repository exposes owner-aware operations instead of loading all records
and rewriting the table:

- List all records, or list records for one owner ID.
- Insert one record with an explicit owner ID while preserving display order.
- Find and delete one record, optionally constrained to an owner ID.

All mutations are transactional. Deletion returns the deleted serialized
record so the management service can remove its files only after database
authorization succeeds.

Deleting a user who still owns image records returns HTTP 409. This preserves
referential integrity in both fresh databases and the deployed database rather
than orphaning images or silently changing their owner.

## Authentication and Identity

The existing login endpoint already returns a random token, but the backend
does not retain or validate it. Extend the authentication service with a
process-local session registry that maps each issued token to a user ID. A
session lookup reloads the user row so role changes take effect without a new
login.

Protected requests send `Authorization: Bearer <token>`. A shared FastAPI
dependency validates the token and provides an immutable current-user value
containing the numeric ID, username, and current role. Missing, malformed,
unknown, or stale tokens return HTTP 401.

Sessions intentionally expire when the application process restarts. The
frontend removes its cached user and shows the login overlay after a 401.
Persistent sessions are not required for this change.

## Upload Data Flow

`POST /api/watermark/embed` requires the current-user dependency. The route
passes the authenticated numeric user ID separately from the existing
watermark form `user_id` value.

The watermark service continues using the form value for the embedded payload
and serialized trace metadata. When it persists the completed record, it
passes the authenticated user ID as the relational owner. Changing the form
value therefore cannot change image-management ownership.

## Image Management Rules

`GET /api/images` requires an authenticated user:

- Role `admin`: query all image records.
- Every other role: query only rows whose relational `user_id` equals the
  current user's numeric ID.

The response shape stays unchanged. `items` contains only visible records, and
`total`, status counts, and today's count are calculated from that same
visible set. Detection attempt and success counters remain system-wide because
they are not attributed to individual image records.

`DELETE /api/images/{image_id}` applies the same rule:

- Administrators may delete any existing image.
- Other roles may delete only a row owned by their current user ID.
- A missing image and an image owned by another user both return HTTP 404 with
  the existing not-found response, so the endpoint does not disclose another
  user's record IDs.

Only after the constrained database deletion succeeds may the service unlink
the record's original, watermarked, and thumbnail files.

## Frontend Integration

The API client reads the token from the stored current-user object and adds a
Bearer header to application API requests. The login request remains
unauthenticated. Existing view functions do not accept username or role
parameters, so callers cannot choose an ownership scope.

On HTTP 401, the client clears the stored current user and signals the root
application state to reopen the login overlay. Normal non-authentication errors
keep the current error handling.

No image-management layout change is required.

## Error Handling

- Administrator missing during backfill: fail startup without printing
  credentials.
- Invalid relational image owner: fail startup and report the image-record ID.
- Invalid or expired login token: HTTP 401 and frontend reauthentication.
- Unauthorized image list access: HTTP 401, never an unfiltered response.
- Unauthorized image deletion: HTTP 404, with no database or filesystem
  mutation.
- Attempt to delete a user who owns images: HTTP 409, with no ownership
  changes.
- Database failure during insert, filter, backfill, or delete: roll back the
  transaction and return the existing service error path.

## Testing

Automated tests cover:

- The database model maps `users.id` and `image_records.user_id` correctly.
- Startup backfills null image owners to the configured administrator and is
  idempotent without changing existing non-null owners.
- Startup rejects duplicate usernames and orphaned image-owner IDs.
- Login tokens resolve to the correct numeric user ID and reject invalid
  tokens.
- A new upload is owned by the authenticated user even when the watermark form
  contains a different `user_id` value.
- Administrators receive every image and global image counts.
- Non-administrators receive only their images and statistics calculated from
  those images.
- Non-administrators can delete their own image but receive HTTP 404 for
  another user's image, with the row and files preserved.
- A user who owns images cannot be deleted.
- The frontend sends the Bearer token and clears stale login state on HTTP 401.

Focused backend and frontend contract tests run first, followed by the complete
test suite. The deployed database is inspected after startup to confirm that
the six historical rows reference the administrator and no orphaned owner IDs
remain.

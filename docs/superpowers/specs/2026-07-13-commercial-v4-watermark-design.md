# Commercial V4 Watermark Design

**Date:** 2026-07-13  
**Status:** Approved by user  
**Target delivery:** Single-customer private deployment, one organization, multiple accounts

## 1. Objective

Build a new v4 watermark format that reaches a measurable commercial acceptance threshold for two primary scenarios:

1. Images propagated through real social and content platforms, including WeChat, browsers, and the selected video/content platform.
2. Local screenshot attribution after 30%, 50%, and 80% cropping combined with common scaling.

The first milestone is algorithm qualification. Application security remains a release blocker and must be completed after the algorithm gate and before any public or customer production deployment.

V4 does not need to detect images generated by v1, v2, or v3. Historical formats may remain available only for isolated comparison during development and are disabled in the commercial request path.

## 2. Mandatory Pre-Change Backup

No implementation file may be changed until the current source has been archived as:

`backups/trace-v3-source-20260713.zip`

This is a **SENSITIVE rollback source archive**, not a secret-free archive. It preserves the exact legacy source needed for rollback, including source-embedded or documented default credentials that existed at capture time. It excludes:

- `data/`, `uploads/`, `output/`, and `test_output/`

Access to the archive must be restricted. All embedded/default credentials retained by the legacy source must be removed or rotated before any production deployment; the archive must never be deployed as application content.

The backup step must also produce:

- `backups/trace-v3-source-20260713.manifest.txt`, containing the sorted archive file list
- `backups/SHA256SUMS`, containing the archive SHA-256 digest
- a successful extraction and file-list verification in a temporary directory outside the project tree

Implementation begins only after all three checks succeed.

## 3. Technical Direction

V4 is a new synchronized, error-correcting, authenticated watermark. It replaces incremental tuning of the existing v3 path.

The payload contains a format version, trace digest, and server-generated authentication tag. The payload is error-correction encoded and interleaved across spatial tiles. A separate synchronization template provides scale, phase, and crop-location recovery.

The authentication key is read only from a server-side environment variable. It must not be stored in image records, returned by an API, embedded directly in source code, or written into benchmark reports.

### 3.1 Detection Pipeline

The detector uses one fixed evidence path:

```text
input validation
  -> content-feature candidate selection
  -> geometric alignment and scale estimation
  -> synchronization recovery
  -> multi-tile soft-decision aggregation
  -> ECC decoding
  -> authentication-tag verification
  -> unique candidate confirmation
```

Content similarity and original-image comparison may reduce the candidate set but can never attribute a trace by themselves.

The detector returns "not detected" when evidence is insufficient, ECC decoding fails, authentication fails, the time budget expires, or more than one candidate validates. It must never choose the visually nearest trace as a fallback.

### 3.2 Module Boundaries

V4 implementation is isolated from the existing monolithic application:

```text
watermark_v4/
  config.py   versioned algorithm parameters and compute budgets
  payload.py  payload encoding, ECC, authentication, and verification
  sync.py     synchronization template and scale/phase recovery
  embed.py    tile interleaving and image embedding
  detect.py   candidate selection, alignment, soft decoding, and attribution
```

The FastAPI layer validates requests, invokes the v4 interface, and persists records. It does not contain v4 signal-processing logic.

## 4. Test Data Strategy

Two separate suites are required.

### 4.1 Fast Regression Suite

Programmatic transformations simulate platform compression, re-encoding, scaling, screenshots, and cropping. This suite runs during development and identifies regressions quickly. It is not sufficient for a commercial release claim.

### 4.2 Release Acceptance Suite

Release acceptance uses images manually propagated through real WeChat, browser, and selected target-platform workflows, plus real screenshot crops. These results are the release source of truth.

Positive samples cover photographs, illustrations, UI screenshots, low-texture images, and high-texture images. Each source is generated with multiple random trace IDs. Crop ratios are 30%, 50%, and 80%, combined with 0.5x, 1.0x, and 1.5x scaling where the resulting image remains meaningful.

The negative set contains 300 images distributed across the same content categories, including similar compositions. It also contains derived platform-compressed, scaled, and cropped variants. A 100-image subset may be used as a development gate, but release acceptance always runs all 300 images.

## 5. Commercial Algorithm Gates

V4 qualifies only when one reproducible release run meets every gate:

| Metric | Required result |
| --- | ---: |
| Real platform propagation correct recall | >= 95% |
| 50% crop correct recall | >= 95% |
| 80% crop correct recall | >= 95% |
| 30% crop correct recall | >= 80% |
| Wrong-trace attribution across positive cases | 0 |
| False positives across 300 negative images | 0 |
| Minimum PSNR | >= 38 dB |
| Minimum SSIM | >= 0.95 |
| Online detection latency P95 | <= 5 seconds |
| Per-case hard timeout | <= 8 seconds |

Increasing watermark strength is not acceptable when it violates either image-quality gate. Reducing attribution checks is not acceptable when it creates wrong-trace or negative-set hits.

## 6. Reports and Reproducibility

Every benchmark emits JSON, CSV, and Markdown outputs with:

- algorithm version and non-secret configuration
- dataset identifier and sample category
- random seed and generated trace ID
- transformation or real propagation route
- expected and detected trace IDs
- detection method, outcome, and elapsed time
- PSNR and SSIM for generated images
- aggregate recall, false-positive count, wrong-trace count, and latency percentiles
- retained failure artifacts

Simulated and real propagation results are reported separately. Reports must not combine them into a single number that obscures real-platform performance.

## 7. Error Semantics

External API outcomes are limited to:

- invalid input
- not detected
- detection budget exceeded
- system error

External responses do not expose authentication material, full candidate lists, or sensitive internal thresholds. Detailed diagnostics are restricted to controlled benchmark outputs and future audit logs.

## 8. Iteration Priority

### Phase 0A: Preserve and Baseline

1. Create, access-restrict, and verify the SENSITIVE V3 rollback source archive.
2. Fix the current default-version test/configuration drift so the baseline has one explicit meaning.
3. Standardize benchmark schemas and commands.
4. Create the simulated suite, real-propagation intake structure, and 100/300-image negative manifests.
5. Capture a reproducible pre-v4 baseline.

### Phase 0B: Build V4 Core

1. Implement and test versioned payload encoding, ECC, and authentication.
2. Implement and test synchronization embedding and recovery.
3. Implement and test interleaved multi-tile embedding.
4. Implement and test budgeted detection and unique attribution.
5. Route new generation and detection through v4 while disabling legacy commercial fallbacks.

### Phase 1A: Joint Optimization

Optimize synchronization, tile layout, ECC parameters, and candidate ordering against recall, false attribution, image quality, and latency together. Every parameter change must run all four gate classes. No single-metric optimization is accepted.

### Phase 1B: Real-Route Acceptance

Run the real WeChat, browser, and target-platform matrix, all crop/scale combinations, multiple random traces, and the full 300-image negative set. V4 is marked algorithm-qualified only after every gate passes in the same release run.

### Phase 2: Commercial Security and Production Readiness

Algorithm qualification does not authorize deployment. Before external use, the application must add:

- server-enforced authentication and RBAC
- password hashing and removal of built-in credentials
- authentication-key lifecycle and secret management
- upload byte, pixel, format, and concurrency limits
- SSRF protection for URL ingestion
- removal or strict protection of development reset endpoints
- audit logging
- background compute workers and bounded queues
- TLS termination, health checks, metrics, alerting, backups, and restore tests

The product remains internal-only until Phase 2 passes its own security and operations acceptance plan.

## 9. Development Rules

- Use test-driven development for every behavior change: failing test, minimal implementation, passing focused test, then regression verification.
- Keep v4 logic out of `main.py` except for narrow integration calls.
- Do not restore visual-only or residual-only trace attribution.
- Do not introduce secrets into source, fixtures, reports, or normal backup archives. The access-restricted V3 rollback archive is a documented legacy exception because exact rollback preserves pre-existing source-embedded/default credentials; rotate those credentials before production.
- Record plan status and benchmark evidence after each completed task.
- Because this directory currently has no Git metadata, local versioned documents and checksums provide the audit trail until version control is initialized.

## 10. Completion Definition

The algorithm milestone is complete only when the same v4 configuration passes all Section 5 gates on the release acceptance suite and the report artifacts are retained. The commercial product milestone is complete only after the separate Phase 2 security and production-readiness plan also passes.
